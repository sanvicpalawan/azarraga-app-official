# Azarraga App — Tech Stack & Code Tree

> Historical architecture snapshot: default product counts and demo-seeding details below are obsolete. The active catalog starts empty; see README.md and `lib/catalog-seed.ts`.

Reference map of the codebase, generated by reading the source at commit `531916d`
(branch `arena/01a0c60d-azarraga-app-official`).

**What the app is:** a single-page quotation and estimation system for *Azarraga Glass &
Aluminum Supply* — browse a product catalog, configure a fabrication (dimensions, series,
glass, color, lock), price it by square foot or by unit, print/export a quotation PDF, and
manage catalog + company data from a built-in admin dashboard.

### Persistence strategy (the one design decision that shapes everything)

`lib/catalog-store.ts` is a thin façade over a `CatalogBackend` interface. At first call it
picks exactly one implementation:

- **`DATABASE_URL` set → `lib/catalog-db-store.ts`** — Neon Postgres for catalog,
  settings, quotations, and image bytes for products and the company logo.
  DDL is idempotent
  and the default catalog is auto-seeded in one transaction on first use (`lib/db.ts`), so
  there is no migration step.
- **`DATABASE_URL` absent → `lib/catalog-memory-store.ts`** — same behaviour, all state in
  a process-global. `pnpm dev` works with zero backend setup; writes do not persist.

Both backends must satisfy `CatalogBackend` in `lib/catalog-store-types.ts`, and both seed
from the single source of truth `lib/catalog-seed.ts` (3 categories, 21 attributes,
28 products, ₱1,850 four-panel window).

### Installed but not used by app code

These are in `package.json` (25 deps / 10 dev deps) because shadcn's registry components
reference them. Nothing in `app/` or `components/admin-dashboard.tsx` imports them — they
are exercised only by vendored files under `components/ui/`:

`date-fns` (no file at all), `recharts` → `ui/chart.tsx`, `react-hook-form` +
`@hookform/resolvers` → `ui/form.tsx`, `cmdk` → `ui/command.tsx`, `vaul` →
`ui/drawer.tsx`, `embla-carousel-react` → `ui/carousel.tsx`, `sonner` + `next-themes` →
`ui/sonner.tsx`, `input-otp` → `ui/input-otp.tsx`, `react-day-picker` → `ui/calendar.tsx`,
`react-resizable-panels` → `ui/resizable.tsx`, `tw-animate-css` → `app/globals.css`,
`@base-ui/react` → `ui/combobox.tsx`, `@shadcn/react` → `ui/message-scroller.tsx`.

**Only 6 of the 61 components in `components/ui/` are reachable from app code**:
`button`, `input`, `label`, `radio-group`, `select`, `textarea`. The other 55 are dormant
(see §4). `hooks/use-mobile.ts` is imported only by the dormant `ui/sidebar.tsx`, so it too
is currently dead weight.

## 2. Request flow

```text
Browser
  │
  ├─ app/page.tsx  ("use client", one component, 4 screens: catalog → configure → preview → admin)
  │     state: catalog, product, width/height/quantity/rate/discount, series/glass/color/lock,
  │            customer + project fields, saveStatus
  │     derived (useMemo): totals (area, subtotal, discount, grand total), filtered products,
  │            grouped attributes
  │     window.modelContext.registerTool("read_product_catalog")  ← optional AI tool hook
  │
  └─ components/admin-dashboard.tsx  ("use client" — overview | company | products | attributes tabs)
        fetches /api/admin/overview; PUTs settings; CRUDs products/categories/attributes;
        normalizes uploads to 900×675 PNG via <canvas> before POSTing
                │
                ▼  fetch() — all calls are relative, no client-side secrets
        ┌──────────────────────────────────────────────────────────────┐
        │  app/api/**/route.ts  (12 route handlers, all force-dynamic)  │
        │   • Zod validates every write body                            │
        │   • errors → 400 (bad input) / 409 (conflict) / 503 (storage) │
        └──────────────────────────────────────────────────────────────┘
                │
                ▼
        lib/catalog-store.ts  ─ facade + parseId() + productImageUrl()
                │
        process.env.DATABASE_URL ?
          ├─ yes → lib/catalog-db-store.ts
          │          └── lib/db.ts   (neon(), DDL, readySchema(), transactional seed,
          │                             files table holding image bytes as base64 text)
          └─ no  → lib/catalog-memory-store.ts  (process-global Maps/arrays)
```

Client-visible data never touches Postgres from the browser: images are proxied through
`/api/products/[id]/image` and `/api/admin/settings/logo`, which stream the stored bytes
(`cache-control: public, max-age=3600` + ETag). `settings.logoKey` decides whether the UI
shows the uploaded logo or the bundled `/azarraga-logo-full.jpg` / `-mark.jpg`.

## 5. Data model (Neon Postgres)

Created idempotently by `DDL_STATEMENTS` in `lib/db.ts`; seeded once in a transaction from
`lib/catalog-seed.ts` when both `products` and `settings` are empty.

| Table | Key columns | Notes |
| --- | --- | --- |
| `categories` | `id` identity PK, `name` unique, `sort_order` | 3 seeded: Windows, Doors, Others |
| `attributes` | `id` identity PK, `type` ∈ `series\|glass\|color\|lock` (CHECK), `name`, `sort_order`, unique `(type, name)` | 21 seeded (13 series, 3 glass, 3 color, 2 lock) |
| `products` | `id` identity PK, `name`, `category_id` FK, `base_price numeric(12,2)`, `description`, `default_series_id`/`default_glass_id` FK → attributes, `image_key`, `image_path`, `updated_at` timestamptz, unique `(category_id, name)` | 28 seeded; image resolves `image_key` (a `media` row) → `/api/products/:id/image`, else `image_path` (bundled art) → `public/` |
| `files` | `key` text PK (e.g. `library/<uuid>.png`), `content_type`, `size_bytes`, `data` (base64 text), `created_at` | Where the image bytes actually live — inside the database, so no object-storage provider is needed. Every product photo and the company logo is a row here |
| `media` | `id` identity PK, `key` unique (points at a `files` row), `filename`, `content_type`, `size_bytes`, `created_at` | The image library. Product photos live here too: `products.image_key` points at a `media.key`, which is how one image can be reused by several products. Deleting a library image is refused while a product still points at it |
| `settings` | `id` PK (single row), `company_name`, `logo_key`, address/contact/email/tin, four bank fields, `terms_conditions`, `pdf_header`, `updated_at` | Drives the printable quotation header, bank box, and terms |
| `quotations` | `id` identity PK, `quotation_number` unique, customer/project fields, `subtotal`, `discount`, `grand_total`, `total_sqft` numeric(12,2), `item jsonb`, `status` default `'draft'`, timestamps | Item detail stored as JSONB — one row per quotation |

Seeding also calls `setval(pg_get_serial_sequence(...))` for `categories`, `attributes`,
`products`, and `quotations` so explicitly seeded IDs don't collide with later identity values.

## 8. Observations worth knowing

- **`app/page.tsx` is the whole frontend and it is dense** — 150 lines with most blocks on a
  single line (JSX, state, helpers, the printable quotation template). Any feature work here
  is the highest-friction change in the repo; splitting the catalog/configure/preview/admin
  screens into real components is the obvious refactor if this grows.
- **Styling splits in two layers**: Tailwind utility classes inline plus ~120 bespoke classes
  in `app/globals.css`. The bespoke layer carries the print/PDF rules, so printing behaviour
  lives in CSS, not in the React tree.
- **`GET /api/products/:id` does not exist** (405) — a pre-existing gap noted in `HANDOFF.md`;
  clients use the `GET /api/products` list or the `/api/catalog` snapshot.
- **Error posture is deliberate**: read routes return 503 with a human-readable message when
  storage is unreachable, and the UI renders that message instead of crashing.
- **Auto-migration means deploy is stateless**: first request after a cold start creates the
  schema and seeds the catalog; `readySchema()` memoises per process and does not cache
  failures, so a bad `DATABASE_URL` retries on the next request.
- **The four-panel window image (891 KB PNG) is the single heaviest asset** in `public/` and
  is served unoptimized: the app uses plain `<img>` in six places (four in `app/page.tsx`,
  two in `components/admin-dashboard.tsx`) instead of `next/image`, which is what the Next
  lint config warns about. `file.svg`, `globe.svg`, and `window.svg` are unreferenced
  Next.js starter leftovers in `public/`.
- **Undeclared integration point**: `app/page.tsx` registers a `read_product_catalog` tool on
  `window.modelContext` when the host provides it; nothing in the repo defines that API.
- **No CI config**: there is no `.github/` directory, so `lint`, `tsc`, and `build` run only
  locally or through Vercel's build.
